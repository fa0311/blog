# GitHubでカレンダー管理をしてみた

## きっかけ

ずのさーで、みんなで共通のカレンダーを管理したいという話になりました。
技術イベントやコミケなどのイベント情報を共有できたら便利だなというところから始まっています。

Googleカレンダーを使っているメンバーが多いので、はじめはGoogleカレンダーで共有しようという話になったのですが、宗教上の都合でGoogleカレンダーを使えないメンバーがいたので困りました。

一方でずのさーは、過去にMinecraftサーバーを建てた際に、タスクをGitHubのIssues/Projectsで管理していたことがあります。
カンバン方式でタスクを管理するのはそれなりに便利でした。

GoogleカレンダーかGitHubかの2択になった際に、最終的にGitHubでカレンダーを管理することにしました。
全員GitHubアカウントは持っているし、GitHubを宗教上の都合で使えない人はいませんでした。

また、icsというカレンダーのデータ形式があることを知り、icsファイルをGitHubで管理して公開しておけば、GoogleカレンダーやApple カレンダー、Outlookなどのカレンダーサービスから購読できることもわかりました。
つまり「予定はGitHubのIssueに書く、見るのはいつものカレンダーアプリ」ができるということです。

余談ですが、この話が出た直後にずのさーの他のメンバーがAIでics生成の仕組みを作ってPRを出してきたのですが、あまりにもAI Slopだったので私が作成し直しました。

## IssuesとProjectsの同期

そもそも、GitHubのIssuesとProjectsの同期がよくわかっていませんでした。
Minecraftサーバーの際には、なんとなくで運用していたので、調べる必要がありました。

### ProjectsのFieldとIssuesのField

Projectsには、Fieldという値を持たせることができます。
これは、タスクの状態や優先度などを表すために使われます。
また、IssuesとProjectsは連携させることができます。

そしてIssuesにも、organizationであれば、Fieldを持たせることができます（Issue Fields）。
2026年5月に全organizationでpublic previewになって、7月にGAになったばかりの新機能です。
個人アカウントのリポジトリでは使えないので注意が必要です。

最初はProjectsのFieldで作っていました。
しかし、ProjectsのFieldはIssuesと相性があまり良くなく、Issuesの検索機能などでの絞り込みができません。
データの実体がProjectの側にあるので、Issueを見ても日付が分かりづらいし、APIもProject経由で叩く必要があって面倒でした。
一方、IssuesのFieldは、Issueそのものに値が付くので、Issuesの検索機能で絞り込みができます。

なので今回は、IssuesのFieldを使って、イベントの日付や場所などを管理することにしました。
作ってから1日でProjectsのFieldからIssue Fieldsに移行しました。

### Issue Fieldsの構造

しかし、IssuesのFieldはなかなかの曲者です。

1つのIssueに対して、1つのIssue Typeを設定でき、Issue TypeごとにFieldをピン留めすることができます。
ピン留めされたFieldだけが、そのTypeのIssueのサイドバーに表示されます。

zodでのイメージは以下のような感じです。

```ts
const Priority = z.enum(["Urgent", "High", "Medium", "Low"]).optional();
const Effort = z.enum(["High", "Medium", "Low"]).optional();
const StartDate = z.iso.date().optional();
const TargetDate = z.iso.date().optional();

const Task = z.looseObject({
  priority: Priority,
  effort: Effort,
});

const Bug = z.looseObject({
  priority: Priority,
  effort: Effort,
});

const Feature = z.looseObject({
  priority: Priority,
  effort: Effort,
  startDate: StartDate,
  targetDate: TargetDate,
});

const IssueFields = z.union([Task, Bug, Feature]).optional();
```

上の例はデフォルトの構造で、organizationを作ると Priority / Effort / Start date / Target date の4つのFieldと、Task / Bug / Feature の3つのIssue Typeが最初から生えています。

しかしFieldの定義はorganizationの設定であり、リポジトリごとに設定することはできません。
Fieldの設定は全てのorganizationのリポジトリに適用されることに注意してください。
Fieldは1 organizationにつき25個まで、型は Single select / Text / Number / Date の4種類、1つのTypeにピン留めできるFieldは10個までです。

### ずのさーのField構成

```ts
const Location = z.string().optional();
const DateStatus = z.enum(["Next", "Error"]).optional();

const Calendar = z.looseObject({
  location: Location,
  startDate: StartDate,
  targetDate: TargetDate,
  dateStatus: DateStatus,
});
```

ずのさーでは、`Calendar` というIssue Typeを作って、上のような構造で、イベントの場所や開始日、終了日、日付の状態を持たせることにしました。

Start dateとTarget dateは、カレンダーに表示するために必要な情報です。
ICS形式ではLocationを扱えるので、Locationも持たせています。

Date statusは自動化のために作ったFieldで、人間が触る用ではありません。
日付が片方しか入っていなかったり、開始日が終了日より後だったりすると `Error`、問題なければ `Next` が自動で入ります（後述）。
人間は `Error` になっているIssueを直すだけでいいです。

### Issue Template

Issue Templateを作成することで、デフォルトのTypeを指定できます。
TypeがCalendarじゃないと、Fieldsが表示されないので、Templateを作っておくと便利です。

```md
---
name: 📅 予定
about: カレンダーに載せる予定を追加する。日付は作成画面下の Fields (Start date / Target date) で設定する
type: Calendar
---
```

Fieldsの値を必須にしたり、Templateで初期値を入れたりすることは無理らしいです、残念。
なので「日付を入れ忘れたIssue」は普通に生まれます。Date statusが必要になった理由がこれです。

### ハマりどころ

publicリポジトリでは、Fieldの可視性を `Public` にしないとorganizationのメンバー以外にはFieldが見えません。
デフォルトは `Organization only` なので、ずのさーのカレンダーを外から見ると日付が見えない、ということが起きました。

ちなみに、IssuesのFieldは、GitHubのGraphQL APIで取得することができます。
`issueFieldValues` というのが生えていて、Date / Single select / Text でそれぞれ型が違うので、fragmentを書き分ける必要があります。
GraphQLのスキーマはまだ新しいので、手元のスキーマが古いと型が出てこなくて少しハマりました。
`@octokit/graphql-schema` ではまだサポートされていませんでした。
コードはずのさーOSSで公開しているため割愛します。

## 作る

まぁこの大AI時代に、手作業でカレンダーを作るはずはなく、AIに作らせたので特に書くことはないです。

### 毎朝の自動化

やっていることは単純で、GitHub Actionsが毎朝9時に動いて、

1. `check`: 全Issueの日付を検査して、Date statusを `Error` / `Next` に更新する
2. `close`: 終了日が過ぎたIssueを自動でcloseする
3. `ics`: `Calendar` typeのopen/closedなIssueからicsファイルを生成する
4. `svg`: 今月と来月のカレンダー画像を生成する

をやってコミットするだけです。

icsは `raw.githubusercontent.com` のURLをそのまま `webcal://` で購読させています。
カレンダーアプリ側が勝手に定期的に取りに来てくれるので、サーバーは一切ありません。

### リマインダー

開始日の3日前と1日前に、Issueの担当者（assignee）全員をコメントでメンションするリマインダーも付けました。
参加するイベントのIssueに自分をassignしておくと、前日にメンションが飛んできます。

### SVG

READMEが寂しかったのでics出力の他に、svg出力も作りました。
Issueに付いたラベルの色でバーが塗られて、ラベルを2つ付けるとグラデーションになるようにしました。
これがめっちゃかっこいいです。
ダークモードにも対応しています。

### ViewsとProjects

また、Issuesの新機能でIssuesのViewsというものが作れます。
これがかなり良くて、Issuesの検索クエリを保存することが出来ます。
`is:issue state:open type:Calendar field."start date":<@today+1m -field."target date":<@today` で、1ヶ月以内に始まってまだ終わっていない予定が見れます。

Projectで扱う際は、Issue Fieldsを設定からProjectのFieldに追加する必要があります。
ガントチャートなどで設定すれば、IssuesのFieldをガントチャートに反映させることができます。
ずのさーでは、Projectはデータを持っていませんが、チャートと値が同期しているので、確認や編集、追加などが行なえます。

## 余談

最近、小さいプロジェクトでも細かくパッケージを分けることにハマっています。
このプロジェクトでも細かくパッケージを分けてWorkspaceで管理しています。
core、github、cli、ics、svg、utils などのパッケージに分けています。

普通に考えると、やりすぎに見えると思います。
クリーンアーキテクチャを厳密にしているわけでもないし、DDDをやっているわけでもないです。
このプロジェクトではGitHub自体がビジネスの中心なので無理に抽象化するのもおかしいです。

では何故パッケージを分けているのでしょうか。

その理由は、AIにどこまでコードを書かせるかの境界を作りたかったからだったりします。
これを勝手にAI汚染境界と呼んでいます。流行らせたい。

core はカレンダーとしての振る舞いやデータの解釈を持つ部分で、人間がしっかりコードを書いています。
一方で github や cli はかなりAIに書かせていて、ics や svg は全部AI生成でレビューすらしていません。

その代わり最終的な出力は人間が確認しています。
svgは目で見ればわかるし、icsはカレンダーアプリに食わせれば正しいかどうかすぐわかります。

つまりこの構成では、パッケージ境界が単なる責務の境界だけではなく、コードに対してどの程度の人間レビューを要求するかという信頼境界にもなっています。

外部ライブラリの内部実装をすべて読まずに使うのと同じように、AIが生成した周辺コードも、小さなインターフェースの向こう側に閉じ込めてブラックボックスとして扱います。
人間の認知コストは、できるだけ core のような重要な部分に集中させます。

## まとめ

この記事で書いたことは全部で3日くらいでできました。
AI SlopなPRをREJECTするところから始まって、Projects版を作って、Issue Fieldsに移行して、svgとリマインダーが付くまでが3日です。
ノリではじめたのですが、思ったよりも便利で、これからも使っていく予定です。

Issueを立てるだけで、カレンダーアプリに予定が生えて、前日にはメンションが飛んできます。
宗教上の都合でGoogleカレンダーが使えなくても問題ないです。

コードもカレンダーも公開しているので、気になったら覗いてみてください。
ずのさーの予定が見たいだけの人は、READMEのリンクから購読できます。
